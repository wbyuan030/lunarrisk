# P3.3 RX7900XT driver maintenance: installed, booted, old runtime functional

2026-11-05/06, following the authenticated candidate plan in [`p33_driver_upgrade_candidate.json`](../protocols/p33_driver_upgrade_candidate.json). The two-package driver30.10.2 transaction completed, both kernels boot-image state was rebuilt, the host rebooted, and both GPUs initialized under amdgpu **6.14.14**. A bounded GPU check in the existing Python3.10/torch2.5.1+rocm6.2 runtime passes. This does **not** establish a NASA-compatible runtime, model execution, training or transfer benefit.

## What ran

1. **Independent backup.** A root backup of both kernel module trees, both vmlinuz/initrd/config pairs, old DKMS firmware, GRUB policy, DKMS/initramfs configuration, AMD package scripts and APT source files was written to ignored `outputs/p33/driver_maintenance_02/backup/old_driver_boot_state.tar.gz`, then re-read and compared entry-by-entry against the live sources: 16,088 entries including 13,628 regular files with matching SHA256, permissions, owners, mtimes and link targets. Archive SHA256 `0901f4def8ddd02cdbca1e012e785ff945caf9302d28270a5cd791af81c93f1c`, 664,326,134 bytes. Two earlier failures (an unreadable vmlinuz at ordinary-user privilege, then a self-written verifier that compared tar type bits to permission bits) are preserved with their partial outputs rather than rewritten.
2. **Stale maintenance record.** `/var/tmp/amdgpu-dkms-kernels` pointed only at the removed `6.8.0-48-generic`. It was replaced with the actual installed `6.8.0-124-generic` and `6.8.0-138-generic`, atomically, after re-verifying the backup and current package identity. Receipt: `REPAIRED_AND_VERIFIED`.
3. **Package transaction.** The installed old pair was `1:6.8.5.60204-2070768.22.04`. APT's first attempt aborted before unpacking with `E: Internal Error, Pathname to install is not absolute` (apt 2.4.15 local-deb handoff); package records were unchanged, which was verified. The unchanged two-package target was then installed from the same authenticated absolute local files (`dpkg --install`, firmware first then DKMS), preserving normal dependency checking and no download/global upgrade/autoremove. Result: exactly `amdgpu-dkms 1:6.14.14.30100200-2226257.22.04` and `amdgpu-dkms-firmware 30.10.2.0.30100200-2226257.22.04`, no other package record changed, `dpkg --audit` clean. The firmware version is numerically a downgrade only because the old package carried epoch `1:`.
4. **Both kernels.** DKMS built and installed `6.14.14-2226257.22.04` for 138 during package configuration and for 124 afterwards; `modinfo` reports version `6.14.14` with each kernel's own vermagic. The old 6.8.5 registration, whose source symlink dangled after the upgrade, was **preserved** (not deleted) with its 16 module/log entries under root-only `/var/lib/p33-driver-recovery/`, removing the `dkms.conf` error from normal status output. The maintenance record was extended back to both kernels and `depmod` plus `update-initramfs` reran for each.
5. **Pre-reboot verification.** Both actual initrds were unpacked and compared: all eight DKMS modules per kernel matched the on-disk SHA256 and vermagic, 660 existing declared firmware payloads matched, `modprobe --show-depends` selected the DKMS module, and no amdgpu blacklist was embedded. Eight declared firmware files absent from the package were traced in the installed source to unrelated ASIC/SRIOV paths, an explicit alternative filename, or a non-default load mode; the actual devices report GC 11.0.0 (7900 XT) and GC 11.0.1 (iGPU), no `amdgpu.*` boot overrides exist, and the missing set matched the reviewed list exactly.
6. **Reboot and runtime check.** The attended reboot booted `6.8.0-138-generic` with amdgpu 6.14.14. Both `03:00.0` (Navi 31 / RX 7900 XT) and `c9:00.0` (Phoenix1 iGPU, boot VGA) bind to `amdgpu`; the iGPU serves the session. `rocminfo` and `rocm-smi` enumerate `gfx1100` and `gfx1103`. A bounded FP32 matmul-by-identity in the pre-existing torch2.5.1+rocm6.2/HIP6.2 environment is exact with synchronization. Kernel log shows no XID, GPU reset, VM fault or call trace.

Observed non-fatal messages: an SMU "driver if version not matched" notice on the dGPU alongside successful SMU initialization and resume; DCN314 register-wait timeouts during iGPU display init, after which the display completed and is in use; absent optional RAP/RAS/SECUREDISPLAY microcode. These are recorded, not classified as failures, and not equivalent to a stability soak.

## Boundaries

The recovery archive is byte-verified but **a restore/fallback boot was not exercised**. Driver maintenance does not establish NASA runtime compatibility: the official package still requires Python>=3.11,<3.13 and torch>=2.12, and the Radeon7.2 guide validates torch2.9.1, below that floor. No NASA environment was created, no checkpoint or weight downloaded, no model constructed, no paired training or cohort scan run, and no budget locked. P3.2 and previous P3.3 results were not rerun or rewritten. Test remains HOLD.
